% Abstract

\begin{abstract}
This is a replication study of ``Compromising Industrial Processes using Web-Based PLC Malware'' (Pickren et al., NDSS 2024), which proposed IronSpider --- a web-based malware that persists within the web interface of modern programmable logic controllers (PLCs) and bypasses factory reset via a Service Worker resurrection scheme.  
%
This study reproduces the paper's firmware complexity analysis (E1) across four WAGO 750-8XXX firmware versions ranging from 2019 to 2023, conducts additional qualitative analysis on firmware JavaScript API features, and creates a standalone browser testbed for the full six-step resurrection cycle (E4) including survival of hardware replacement.
%
Furthermore, this study implements the three key attack capabilities inspired by IronSpider --- sensor spoofing, alarm suppression, and actuator manipulation --- by manual malware injection, which is analogous to CVE-driven code injection in the paper.
%
Finally, this study strives to solve the paper's open detection problem of web-based PLC malware by implementing a server-side runtime detector inside OpenPLC's Flask webserver. Tier~1 alert shows zero false positive over five minutes of normal operation by setting up detection logic for two request headers: \texttt{Sec-Fetch-Dest: empty} and a \texttt{Referer} originating from a \texttt{.js} context. The detection technique is evaluated with three evasion methods, two of which defeat Tier~1 with suggestions on countermeasures. 
\end{abstract}

\begin{IEEEkeywords}
PLC malware, industrial control systems, Service Worker, web security,
behavioural detection, ICS
\end{IEEEkeywords}

% I. Introduction
% ---------------------------------------------------------------
\section{Introduction}

Industrial control systems (ICSs) are the backbone of critical infrastructures such as water treatment plants, power grids, and manufacturing factories. They have been considered to be free of web-based attack vectors, due to its traditional isolation from the open Internet. However, this assumption has become obsolete as modern PLCs gradually provide more support for browser-based human-machine interfaces (HMIs) and embedded web servers, which allow for remote system monitoring and configuration. The boundary between operational technology (OT) and information technology (IT) is fading, and ICSs are now open to web-based attack.

Pickren et al.~\cite{ironspider2024} proposed IronSpider, a
web-based PLC malware (WB PLC malware) that hinders the system entirely within the
operator's browser. Unlike traditional PLC malware (e.g., Stuxnet~\cite{stuxnet}, HARVEY~\cite{harvey2017}), IronSpider does not require prior knowledge of firmware or kernel exploits; it only utilises browser APIs to control the system as if it were a legitimate human operator. The paper demonstrates key attack capabilities such as sensor spoofing and actuator manipulation, along with a Service Worker (SW) resurrection mechanism that revives the malware after factory reset, surviving even hardware replacement. Another key finding is that four established JavaScript malware detectors (Cujo, Zozzle, JaSt, JStap) all failed to categorise IronSpider as malicious, since the malware does not contain any aggressive or syntactically suspicious code patterns \cite{ironspider2024}.

This study contains a structured replication study conducted over
19 days with four contributions:
\begin{enumerate}
  \item \textbf{Firmware growth analysis (E1).} This study replicates the paper's SLOC and cyclomatic complexity measurements on four WAGO firmware versions (two from the paper, two intermediate chosen by this study). Also, we extend the analysis qualitatively by observing any change in JavaScript API surface between versions. 
  \item \textbf{Service Worker resurrection testbed (E4).} 
      This study builds a standalone Node.js/HTTPS testbed showing the full six-step resurrection process of WB PLC malware and demonstrate hardware replacement survival and the 24-hour cache limit of SWs.

  \item \textbf{OpenPLC capability demonstration.} 
      This study implements the three key attack capabilities of IronSpider on OpenPLC via manual payload injection --- an adaptation which preserves the attack characteristics while acknowledging that CVE-driven code injection in OpenPLC is not feasible, unlike in the original paper's case.

  \item \textbf{Behavioural anomaly detection.} This study implements a server-side detector as a component of OpenPLC's Flask webserver, addressing the detection gap stated in the paper. The Tier~1 heuristic makes use of browser-generated Fetch Metadata headers to detect SW constantly checking for the malware's presence, while keeping the number of false positives to zero.
\end{enumerate}

The remainder of the paper is organised as follows.
Section~\ref{sec:background} covers background on ICS architecture,
WB PLC malware, and the OpenPLC browser APIs exploited.
Section~\ref{sec:methodology} describes the test environment and experimental
adaptations.
Sections~\ref{sec:e1}--\ref{sec:detection} present results.
Section~\ref{sec:discussion} discusses implications and limitations.
Section~\ref{sec:conclusion} concludes.

% II. Background
% ---------------------------------------------------------------
\section{Background}
\label{sec:background}

\subsection{ICS Architecture and the PERA Model}

Industrial control systems typically adopt the Purdue Enterprise Reference Architecture (PERA) model, which categorises assets into five levels: Level~0 (field devices and sensors),
Level~1 (basic control including PLCs, RTUs), Level~2 (supervisory control including
HMIs, SCADA), Level~3 (site operations network), and Level~4 (enterprise
network). WB PLC malware places itself entirely within the OT boundary (Level~2), spoofing HMI values and controlling actuators.

\subsection{Web-Based PLC Malware vs.\ Traditional PLC Malware}

Traditional PLC malware (e.g., Stuxnet~\cite{stuxnet},
HARVEY~\cite{harvey2017}) often requires specific knowledge about the victim's instruction set and PLC firmware. In comparison, WB PLC malware only exploits the victim browser's web API for spoofing and controlling the underlying physical system, imitating the legitimate human operator behind the HMI.

\subsection{Service Workers and the Resurrection Mechanism}

A Service Worker (SW) is a JavaScript file that the browser registers as a persistent background proxy for a web origin~\cite{w3c-sw}. Key properties that IronSpider exploits:

\begin{itemize}
  \item \textbf{Persistence.}
        SW registrations are stored on the browser's side; deleting the injected SW file from the server does not remove the registered SW.
  \item \textbf{CacheStorage.} SWs can store data in
        \texttt{CacheStorage}, which persists without explicit user action or storage pressure.
  \item \textbf{Same-origin fetch privilege.} 
        A SW registered on the PLC's web context can call any same-origin web API without cross-origin resource sharing (CORS) restriction, exploiting the operator's authenticated session.
  \item \textbf{DOM bypass via \texttt{respondWith}.} 
        SWs do not have direct DOM access, but they can intercept HTTP responses and inject arbitrary JavaScript code. The injected code runs in the page context with full DOM access.
\end{itemize}

The resurrection cycle (Fig.~4 of~\cite{ironspider2024}) works as follows: after initial infection, the SW caches the malware payload in CacheStorage. If a factory reset occurs, the SW detects the 404 after trying to GET the malware. It then retrieves the cached copy, and re-uploads it using the same CVE chain exploited to inject the malware.

\subsection{Static JS Malware Detection and Its Limits}

The paper attempted at detecting IronSpider using four static JavaScript analysers: Cujo~\cite{cujo}, Zozzle~\cite{zozzle}, JaSt~\cite{jast}, and JStap~\cite{jstap}. All four classified IronSpider as benign, since it lacks aggressive indicators such as mining cryptocurrency in WebAssembly.

% III. Methodology
% ---------------------------------------------------------------
\section{Methodology}
\label{sec:methodology}

\subsection{Testbed Overview}

The study uses two separate test environments:

\begin{enumerate}
  \item \textbf{E1 firmware analysis.} WAGO 750-8XXX firmware images v3.0.39 (May 2019) and v4.02.13 (Mar 2023) are the two versions discussed in the original paper. This study additionally analyses two intermediate versions: v3.1.7 (Jul 2019) and v3.09.04 (Mar 2022). These firmware versions are analysed using the paper's published Docker container, with the same SLOC and cyclomatic complexity tools.

  \item \textbf{E4 resurrection testbed.} This study creates a Node.js HTTPS server, which serves a simulated PLC dashboard. Three routes replicate the attack relevant server functionality: \texttt{GET /*} (static file server), \texttt{POST /reset} (factory reset: deletes \texttt{malware.js} from disk), and \texttt{POST /upload} (file write: analogue of CVE-2022-45140 mentioned in~\cite{ironspider2024}).
\end{enumerate}

\subsection{OpenPLC Adaptation}

OpenPLC Runtime v3~\cite{openplc} is an open-source PLC with a Flask-based web interface, which provides a monitor/write API structure. This study installs a water pump ladder logic program (Structured Text) that controls a simulated pump relay (\texttt{\%QX0.0}) based on a water level sensor (\texttt{\%IW0}) with configurable high/low setpoints and an alarm output (\texttt{\%QX0.1}).

\textbf{Adaptation from paper.} The original paper exploits the three-CVE chain to deliver the malware inside the PLC's web directory. OpenPLC's Flask architecture lacks such features; Flask's \texttt{static/} folder is the structural equivalent, but this confines SW scope to \texttt{/static/} rather than \texttt{/}. Accordingly, this study manually injects both the SW registration and IronSpider capabilities directly into \texttt{static/} and loading them on OpenPLC's monitoring page template (\texttt{pages.py}). This simulates the \emph{effect} of the CVE-based delivery, without replicating the delivery mechanism itself. This marks a clear distinction from the paper's original scenario.

\subsection{Detection Extension}

The detector (\texttt{ironspider\_detector.py}) is a Python program included inside OpenPLC's Flask webserver using a \texttt{@before\_request} hook. It adopts three detection tiers of increasing false-positive risk:

\begin{itemize}
  \item \textbf{Tier~1 (deterministic):} This monitors browser-generated headers for incoming GET requests. Alerts are generated when 3 or more requests with \texttt{Sec-Fetch-Dest: empty} and a \texttt{Referer} URL ending in \texttt{.js} arrive within a 90-second sliding window.
  \item \textbf{Tier~2 (statistical):} This monitors whether the rate of \texttt{/point-write} call exceeded 2 writes/second over a 5-second sliding window;
  \item \textbf{Tier~3 (heuristic):} This monitors the latency between a \texttt{/monitor-update} (sensor read) and a subsequent \texttt{/point-write} (actuator write); alerts if under 500~ms.
\end{itemize}

The rationale behind setting up Tier~1 is explained in detail in Section ~\ref{sec:detection}. All the parameters for detection tiers can be configured as constants, and alert outputs are printed to the server console. The alerts are also accessible via a \texttt{/ironspider-alerts} endpoint.

% V. Service Worker Resurrection Testbed (E4)
% ---------------------------------------------------------------
\section{Service Worker Resurrection (E4)}
\label{sec:e4}

\subsection{Six-Step Resurrection Cycle}

This study verified all the steps of the malware resurrection cycle stated in Section~IV-C of~\cite{ironspider2024}:

\begin{enumerate}
  \item \textbf{SW registration.} When loading the page for the first time, the browser fetches \texttt{sw.js} and registers it at scope \texttt{/}. Looking at DevTools confirms ``activated and is running.''
  \item \textbf{Payload delivery.} As \texttt{malware.js} is injected, it starts to execute display spoofing (sensor values turn green) and exfiltration simulation for credentials logged to console.
  \item \textbf{Factory reset.} \texttt{malware.js} from the server, simulating a factory reset. The SW remains registered in the browser profile.
  \item \textbf{SW detects absence.} The SW's \texttt{setInterval} fetches for \texttt{/malware.js} within 5 seconds, and receives HTTP~404.
  \item \textbf{Re-upload.} The SW retrieves the payload from \texttt{CacheStorage} and POSTs it to \texttt{/upload} (this is analogous to the original paper's CVE chain). Server log confirms: ``\texttt{RESURRECTION: wrote malware.js}.''
  \item \textbf{Payload re-execution.} The SW sends \texttt{postMessage(\{type:~'RESURRECTED'\})} to all open tabs. Display spoofing resumes with the re-injected malware.
\end{enumerate}

All six steps above executed autonomously within one SW polling interval of 5~seconds. This confirms the paper's claim on malware resurrection after the factory reset.

\subsection{Hardware Replacement Survival}

This study also evaluated the paper's claim that resurrection survives hardware replacement. This was achieved by simulating full server process replacement:

\begin{enumerate}
  \item Record server PID via \texttt{GET /server-info} (PID~3{,}725{,}031).
  \item Kill the Node.js process (\texttt{Ctrl+C}).
  \item Delete \texttt{malware.js} and \texttt{sw.js} from disk.
  \item Restart the server.
  \item Record new PID (3{,}728{,}686) --- different process confirmed.
\end{enumerate}

The browser's SW registration and activation persisted, despite the complete server replacement. The full resurrection cycle was executed within the SW polling interval, re-uploading both the cached \texttt{malware.js} \emph{and} \texttt{sw.js} to the new server instance. This supports the paper's claim that the SW registration resides in the browser, not the physical device.

\subsection{The 24-Hour Cache Limit}

The paper mentions a ``24-hour cache limit'' as a limitation for SW. This study identified two relevant mechanisms in the W3C SW specification~\cite{w3c-sw} to look into this claim further:

\begin{enumerate}
  \item \textbf{SW script update check interval} (\S9.2): the browser fetches the SW script at most once per 24 hours per navigation, and compares it with the registered SW byte-for-byte. 

  \item \textbf{CacheStorage eviction}: the specification does \emph{not} make a 24-hour eviction policy compulsory. Storage entries are evicted only under explicit user action or storage pressure.
\end{enumerate}

This study empirically confirmed that CacheStorage entries persist across browser tab closure, server restarts, and page refreshes. The only reliable solution to eliminate the SW is explicit SW unregistration via DevTools.

% VI. OpenPLC Capability Demonstration
% ---------------------------------------------------------------
\section{OpenPLC Capability Demonstration}
\label{sec:openplc}

This study implemented and confirmed the functionality of the three key IronSpider capabilities depicted in the original paper. This was achieved on OpenPLC Runtime v3 with a custom water pump control program (\texttt{water\_pump.st}).

\subsection{Capability 1: Sensor Spoofing}

The injected malware wraps the response from \texttt{/monitor-update} by gaining access to the DOM update in the monitoring page. The \texttt{ironspiderSpoof()} function parses the HTML table from the API, finds the row containing \texttt{water\_level}, records the actual value to \texttt{localStorage}, and returns a fabricated reading value before display. The operator observes a normal water level when the actual value may be dangerously high.

\subsection{Capability 2: Alarm Suppression via Spoofing}

When the water level exceeds the alarm threshold of 80, the PLC sets \texttt{alarm\_active} to \texttt{TRUE}. The spoofing function detects the \texttt{bool\_true.png} indicator and replaces with \texttt{bool\_false.png} in the DOM. The operator is not able to see the actual alarm, potentially ignoring a dangerous situation.

\subsection{Capability 3: Actuator Manipulation}

The malware runs a \texttt{setInterval} loop, calling \texttt{/point-write?value=1\&address=\%QX0.0} every 500\,ms. This changes the actual Boolean value for the pump relay, turning it ON regardless of the ladder logic's output. This bypasses the PLC control loop by using the web API.

While testing for this capability, intermittent toggling of \texttt{pump\_running} between TRUE and FALSE was observed. This is due to the PLC's scan cycle writing the actual, computed value to the same address (\texttt{\%QX0.0}). In a real deployment, combining actuator manipulation while spoofing the pump relay reading would hide the override from the operator entirely.

\section{Behavioural Anomaly Detection}
\label{sec:detection}

\subsection{Design Rationale for Tier~1}

The paper leaves detection of IronSpider as an ``open problem'' since IronSpider uses only legitimate browser API with no suspicious patterns detected by JavaScript analysers. This study observed that while the \emph{payload} itself is indistinguishable from benign JavaScript, the \emph{SW polling loop} for the malware may produce distinguishable HTTP request metadata useful for detection.

This study focused on detecting SW-originated fetch using two browser-generated headers:

\begin{itemize}
  \item \textbf{\texttt{Sec-Fetch-Dest: empty}.} This header is set for all \texttt{fetch()} API calls according to the W3C Fetch Metadata specification, while a \texttt{<script src>} tag sets \texttt{Sec-Fetch-Dest: script} instead. JavaScript cannot forge or suppress this header.

  \item \textbf{\texttt{Referer} ending in \texttt{.js}.} \texttt{fetch()} calls initiated by SW sets the SW script URL as Referer (e.g., \texttt{/static/sw.js} in OpenPLC's case). Page-originated \texttt{fetch()} calls have the page URL as the value for Referer (e.g., \texttt{/monitoring}), which does not end in \texttt{.js}.

\end{itemize}

It was found that only having one of the signals inside the detector logic is not sufficient. \texttt{Sec-Fetch-Dest: empty} also matches page-originated \texttt{fetch()} calls, and a \texttt{.js} Referer could theoretically appear in benign SW scenarios. The combination of the two signals facilitates identifying the SW polling loop specific for the WB PLC malware.

\subsubsection{Iterative Development}

The final design for Tier~1 logic was devised after two failed attempts:

\begin{enumerate}
  \item \textbf{Count-based (rejected):} This strived to count all GET requests to \texttt{/static/malware.js}. Not only did it have the name of the malware hardcoded in the detector, but also it falsely categorised the monitoring page's \texttt{<script src>} load as malicious.

  \item \textbf{Cache-Control filter (rejected):} Since the SW polls for the malware using \texttt{cache:~'no-store'}, the request was expected to have \texttt{Cache-Control:~no-cache} in its header. However, this was not included in the actual HTTP request. This is likely due to \texttt{sw.js} setting \texttt{cache:~'no-store'} instead of \texttt{'Cache-Control':~'no-store'}. The cache option controls browser caching behavior internally, not necessarily the HTTP headers.
\end{enumerate}

A debug header dump revealed \texttt{Sec-Fetch-Dest} and
\texttt{Referer} as the possible discriminators, leading to the final design of Tier~1.

\subsection{False Positive Evaluation}

The malware injection was disabled (commented out the relevant malware blocks in \texttt{pages.py}), and removed both \texttt{malware.js} and \texttt{sw.js} from the server. The detector ran for 5 minutes with normal ongoing operations such as monitoring refreshes, manual point writes. This resulted in \textbf{Zero Tier~1 alerts} generated.

\subsection{Evasion Evaluation}

Three evasion techniques were utilised against the Tier~1 detection logic:

\begin{table}[ht]
\centering
\caption{Evasion techniques against the Tier~1 detection.}
\label{tab:evasion}
\small
\begin{tabular}{@{}lp{3.2cm}c@{}}
\toprule
\textbf{Evasion} & \textbf{Technique} & \textbf{Detected?} \\
\midrule
Renaming SW        & Rename \texttt{sw.js} to \texttt{resurrect.js} & Yes \\
Slow polling     & Interval $\to$ 90\,s & No \\
Referer suppress & \texttt{no-referrer} policy & No \\
\bottomrule
\end{tabular}
\end{table}

\textbf{E1 (SW rename):} The detection logic is filename-agnostic --- it looks for any \texttt{.js} signature in the \texttt{Referer} header. The alert fired correctly after renaming the SW.

\textbf{E2 (slow polling):} The detection failed after slowing down the polling requests for the malware to one request per 90 seconds. This never reached the threshold of ~3 requests per 90 seconds.

\emph{Countermeasure:} This evasion can trivially be resolved by changing the threshold to ~1 for the entire duration of server execution. This may come at the cost of potential false negative. The detection window can also be extended beyond 90 seconds.

\textbf{E3 (Referer suppression):} Adding the fetch option of
\texttt{referrerPolicy:~'no-referrer'} in \texttt{sw.js} causes the browser to exclude the \texttt{Referer} header. Tier~1 detection does not function without the Referer to inspect. The detection failed.

\emph{Countermeasure:} The detection logic may be modified to label the \emph{absence} of a Referer header on a \texttt{Sec-Fetch-Dest: empty} request as suspicious. This is possible since legitimate page-originated fetch calls in Chromium-based browsers (Brave, Chrome) include a Referer in same-origin request by default.

% VIII. Discussion
% ---------------------------------------------------------------
\section{Discussion}
\label{sec:discussion}

\subsection{Replication Fidelity}

The E1 results of this study successfully replicated the paper's SLOC and complexity figures, validating the measurement methodology. This study also extended the complexity analysis by analysing two intermediate firmware versions, providing new evidence that the code base expansion was gradual. The increase in web-related content took place primarily during v3.1.7 $\to$ v3.09.04 transition (2019--2022), adding new features including cloud connectivity and Docker support.

The E4 test environment for SW successfully demonstrates all six steps of the SW resurrection cycle. The study also looked into two related mechanisms to the paper's statement about ``24-hour cache limit'', revealing that CacheStorage eviction can \emph{only} take place from an explicit user action or storage pressure.

\subsection{Limitations}

\textbf{OpenPLC adaptation.}
The most notable limitation of this study is the absence of a CVE-based malware injection vector on OpenPLC. The manual injection method simulates the \emph{effect} of the exploit, but does not validate the \emph{injection} mechanism. Due to the Flask architecture of OpenPLC, the SW's scope is also limited to  \texttt{/static/} rather than \texttt{/}; this restricts its ability to intercept all page fetches.

\textbf{Single browser tested.}
The detection logic for Tier~1 (\texttt{Sec-Fetch-Dest} and
\texttt{Referer} behavior) was only validated on Brave browser, which is Chromium-based. Firefox and Safari may set the request headers differently, indicating that changes in detection logic may be necessary when running on these browsers.

\textbf{False positive test scope.}
False positive test scope is limited to five minutes. A production deployment may necessitate multi-day testing, capturing the entire complexity of operator workflows.

\textbf{Tier~2 and Tier~3 not rigorously evaluated.}
This study focused on the evaluation of Tier~1, since it was considered to be the primary indicator of WB PLC malware. Tier~2 (write rate) and Tier~3 (read-write latency) were implemented and observed to produce alerts, but they are not rigorously tested for false positives.

\subsection{Implications for ICS Defence}

The open detection problem stated in the original paper can be addressed by executing a server-side behavioural detection based on Fetch Metadata headers. Since the implementation takes place on the server side, no client-side modification is required for this approach.

The evasion experiment displays that the Referer header can be modified by SW to bypass the detection logic. A more robust design may combine Tier~1 logic with Content Security Policy (CSP) headers that restrict SW registration, or with Subresource Integrity (SRI) checks on the loaded JavaScript files.

% ---------------------------------------------------------------
% IX. Conclusion
% ---------------------------------------------------------------
\section{Conclusion}
\label{sec:conclusion}

This study replicated key experiments from the IronSpider WB PLC malware study, verifying the paper's analysis on PLC firmware's web content complexity, the full SW resurrection cycle including hardware replacement survival, and the three key attack capabilities on an alternative PLC environment (OpenPLC). This study also looked more into the ``24-hour cache limit'' of SW, confirming the SW persistence mechanism through the lens of SW update check interval and CacheStorage eviction.

This paper implemented an example three-tier behavioural, runtime detector for IronSpider, which addresses the open problem of detection gap mentioned in the original paper. Tier~1 logic utilises two Fetch Metadata headers (\texttt{Sec-Fetch-Dest: empty} and a \texttt{.js}-suffixed \texttt{Referer}) to identify SW polling loops. Two of three tested evasion techniques prevent Tier~1 alarm, but both have straightforward countermeasures such as extending the detection window and treating empty Referer headers as potentially malicious.

Future work includes cross-browser validation of the Fetch Metadata headers, integration of Tier~1 with CSP-based SW registration restrictions, and multi-day false positive tests for a production-grade ICS environment.
